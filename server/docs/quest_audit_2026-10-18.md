# Ascendant quest script audit — 2026-10-18 (read-only)

Scope: `/opt/akk-stack/server/quests` (3,889 `.pl`, 4,247 `.lua`). Live server, players online; nothing was edited, reloaded or written to the DB. Evidence came from reading code, `perl -c` / `luac -p` syntax checks, read-only SQL, the C++ tree at `/opt/akk-stack/code` (to confirm engine semantics the scripts rely on), and the zone logs under `server/logs`.

Prior backlog IDs referenced (not re-discovered): PERF-02, PERF-03, COR-01, COR-02 from `docs/modernization_plan.md`; IDLE-03 from `docs/code_audit_2026-10-08.md`. New items use `QA-nn`.

Reload-risk legend: **reload-safe** = `#reloadquest`/`#reloadperl`-class change that only swaps script text (owner policy is still "no hotfix, wait for a normal restart"; the column says what *would* be needed, not that it should be done now). **restart** = needs a zone/world restart or DB flag that only new processes read.

## (c) Findings

Format: ID — title. File:line. Evidence. Confidence. Impact. Smallest fix (not applied). Reload need.

### Confirmed

**QA-01 — Veteran AA grant loop never grants the intended set.**
`global/global_player.pl:185-206`.
```perl
for (my ($aa, $v) = each %vet_aa) {
    if ($v[2] && ($v[1] || $age >= $v[0])) {
        $client->GrantAlternateAdvancementAbility($aa, 1);
```
`for (LIST)` is a foreach over the two-element list returned by the assignment, `$aa` is one arbitrary hash key (hash order), and `$v[2]` reads the (empty) package array `@v`, not `$v->[2]`. The block is above `use strict` (line 319) so nothing complains. DB: `aa_ability` 481–487/511/2000/8081/8130/453/182/600 are `grant_only`, not auto-granted; of 484 characters logged in within 7 days **0** have 481; the only two IDs anyone holds are 483 (532 chars) and 182 (404), and among 325 characters created in the last 14 days just 3 and 2 got one of those — consistent with a random single key firing occasionally.
Confidence: confirmed. Impact: all 14 veteran AAs the code says "grant anyways live test server style" are missing for everyone.
Fix: `foreach my $aa (keys %vet_aa) { my $v = $vet_aa{$aa}; next unless $v->[2]; $client->GrantAlternateAdvancementAbility($aa, 1) if $v->[1] || $age >= $v->[0]; }`. 14 grant calls per login is cheap. Reload: reload-safe (global_player). Grants apply at next login.

**QA-02 — Quest errors are not persisted anywhere.**
`logsys_categories` id 87 QuestErrors: `log_to_console=1, log_to_file=0, log_to_gmsay=1`; id 20 Quests all off. Zone processes are started by `spire-launcher` with stdout → `/dev/null` (checked `/proc/<zone pid>/fd/1`); `docker logs` for the server container has 6 lines in 2 h. Grep of all 1,172 current zone logs (2026-10-17 21:00 → 2026-10-18 21:02) for `[Quests]|[QuestErrors]|Perl|Lua` finds only the "Loaded Perl Event Export Settings" boot line.
Confidence: confirmed. Impact: silent failures (eaten items, undefined-sub dies, Lua nil errors) are only visible to a GM who happens to be online with gmsay.
Fix: `UPDATE logsys_categories SET log_to_file=1 WHERE log_category_id=87` (optionally 20 too). Reload: new zone processes read it at boot; no quest reload. Risk: log volume only.

**QA-03 — Per-spawn DB connection + per-item queries in `global_npc.pl` EVENT_SPAWN; bonus-loot rolls open a connection per attempt (extends PERF-02/PERF-03).**
`global/global_npc.pl:405-437`:
```perl
my $dbh = _get_dbh();          # plugin::LoadMysql(): open eqemu_config.json, JSON decode, DBI->connect
return unless $dbh;
my @loot_list = $npc->GetLootList();
return unless @loot_list;      # too late: the connection is already made for pets, adds, loot-less NPCs
foreach my $item_id (@loot_list) {
    my $sth = $dbh->prepare(q{SELECT tier_code, variant_item_id FROM item_tier_map WHERE base_item_id = ? ...});
```
`plugins/MySQL.pl:5-37` opens a new `DBI->connect` on every call and never caches (PERF-02 still accurate). `plugins/ascendant_loot_utils.pl:947-950` `get_loot_dbh` is just `LoadMysql`, and `get_random_rare_spawn_loottable` (`:617-700`, the PERF-03 `ORDER BY RAND()` six-table join) calls it **per attempt**; `add_rare_spawn_loottable_roll` (`:702-789`) loops up to `$max_attempts=25`, and `common_mob_bonus_loot`/`rare_levelblock_loot` can run it twice → up to 50 connections and 50 random-order joins for one NPC spawn. `common_rare_bonus_item_ids` (`:411-471`) is correctly memoised; the rest is not.
Confidence: confirmed from code (cost not measured on the live DB — no writes/benchmarks were run). Impact: zone boot and respawn churn; `item_tier_map` has 212,130 rows so each per-item lookup is indexed but still a round trip.
Fix (smallest, in order): (1) move `GetLootList`/`return unless @loot_list` above `_get_dbh()`; (2) in `MySQL.pl` keep the handle in a package variable (`our $DBH; return $DBH if $DBH && $DBH->ping;`) — but first remove the three `->disconnect()` calls on shared handles (`global_player.pl:839`, `ascendant_fellowship.pl:147`, `ascendant_insight_trainer.pl:232`) or they will kill the cached handle for everyone; (3) memoise `item_tier_map` results per `base_item_id` in a `my %tier_cache` in global_npc.pl (bounded by distinct items seen in the zone); (4) in `get_random_rare_spawn_loottable`, pass one `$dbh` through the attempt loop. Reload: reload-safe (plugins + global_npc) but (2) touches 46 call sites — do it in a normal restart window.

**QA-04 — Manual `SummonItem` "returns" in hand-in scripts degrade items and eat items in mixed trades (not a dupe).**
`guildlobby/Harley_Wynn.pl:56-61`:
```perl
foreach my $item_id (keys %itemcount) { ... next if $item_id == $LUCKY_COIN_ID;
    quest::summonitem($item_id, $itemcount{$item_id}); }
```
`plugins/ascendant_philanthropist.pl:161-168, 172-179` (`$client->SummonItem($item_id)` for no-trade, `SummonItem($item_id,-1,1)` for attuned), called from `guildlobby/Ben_Affactor.pl:183`.
Engine semantics (verified): `trading.cpp:674-704` returns unconsumed items after EVENT_TRADE when `Items:AlwaysReturnHandins=true` (it is), **unless** `npc.cpp:4668-4684` finds that a script already summoned an item with the same ID — `Client::SummonItem` records every summoned ID (`inventory.cpp:668`) — in which case the engine returns **nothing** for that trade. Consequences: (i) the summoned copy is a new instance: augments, remaining charges, ornamentation and (Harley) attunement are lost; (ii) Harley: `summonitem($id, $count)` for N identical non-stackable items yields one item with `charges=N`; (iii) Harley: 11+ coins handed together with any non-coin item → the loop stops at 10, the engine would have returned the rest but is now suppressed → coins eaten (the "The rest are returned" message is then wrong); (iv) Ben Affactor: same suppression once any no-trade/attuned item was "returned", so a tradeable item in the same trade that `quest::handin` did not consume (e.g. the loop never reached it) is lost. `cshome/Harley_Wynn.pl` is an identical copy.
Confidence: confirmed from code. Impact: destroyed augments/charges on accidental hand-ins; occasional coin loss. Fix: delete the manual summon loops and let the engine return originals (that is exactly what `plugin::return_items` — an empty sub in `plugins/check_handin.pl:21-22` — relies on in 1,483 stock scripts). Reload: reload-safe (guildlobby zone scripts + plugin).

**QA-05 — Mark of Ascendance online timer dies on the first zone change.**
`global/global_player.pl:155-178` starts `moa_online_roll` only in EVENT_CONNECT; `plugins/ascendant_moa_tokens.pl:381-391, 394-404` (re)schedules it only from CONNECT or from its own firing. Engine: EVENT_CONNECT runs under `if (ingame)` (`client_packet.cpp:919-936`), and `client_process.cpp:995` clears `character_data.ingame` on every zone-out "because we only want to trigger it on their first login from world" — so CONNECT fires once per session. Quest timers belong to the per-zone Client object and are not carried across zones; EVENT_ENTERZONE (`:32-79`) never restarts the timer. The pity accumulator (`MoA_UpdatePityAcc`) is only advanced inside the timer handler, so it stalls too. The `moa:<cid>:timer_active` bucket is written but never read.
Confidence: confirmed from code (behaviour, not observed in logs — see QA-02). Impact: the "being online" Mark path only works while a player stays in their login zone; the design README says it should run everywhere.
Fix: call `plugin::MoA_StartOnlineTimer($client)` from EVENT_ENTERZONE (it already stops/restarts safely) instead of / in addition to CONNECT; or persist the next-fire epoch in the existing `timer_active` bucket and reschedule from ENTERZONE with the remaining delay so zoning cannot be used to re-roll. Reload: reload-safe.

**QA-07 — Data-bucket hygiene and uncached non-scoped reads on hot paths.**
`data_buckets`: 366,084 rows; prefixes `player_welcomed_` 29,950 (`global_player.pl:157-172`, 33 rows orphaned to deleted characters), `lore_aa_bonus_cd_` 14,545 (`:710-747`, a 5-minute cooldown stored with no TTL), `asc_auto_skills_` 13,094, `leaderboard_deaths_` 11,631, `pet_equip_cooldown_` 6,840 (`global_npc.pl:510-521`, a 30 s cooldown with no TTL), `leaderboard_upgrade_` 4,978; plus ~60k `classic_/kunark_/velious_/luclin_/pop_*` boss-kill keys. Confidence: confirmed (row counts, cache rule) / likely (perf weight). Fix: add TTLs to cooldown keys (`set_data($key, 1, 30)` / 300), write new per-character state with the scoped API (`$client->SetBucket`/`GetBucket`) so it hits the cache, and a one-off cleanup of orphaned rows. Reload: reload-safe; cleanup is a DB maintenance task.

#### Encounter-scaling plugin family (`ascendant_encounter_scaling{,_luclin,_pop,_loy,_ldon,_god}.pl`) — COR-01 re-verified

Structure: the five variants are mechanical copies of the Velious base with every file-level `my` and private sub renamed, so **file-level data is not shared**. What is shared across all six: the entity-variable names (`enc_scaled`, `enc_profile`, `enc_participants`, `enc_comp_score`, `enc_orig_*`), the timer name `enc_rescan`, and the dispatch in `global_npc.pl:537-586` that calls all six handlers for every NPC.
